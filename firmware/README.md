# KitchenGuard LPG Device Firmware (Component 01)

Production firmware for the ESP32 Dev Kit LPG leak-detection node. It replaces the
digital-threshold prototype with analog MQ-2 sensing, ppm conversion, the 9-feature
pipeline, the on-device classifier slot, the 700 ppm life-safety override, debounced
fan/window/buzzer actuation, and WiFi/MQTT telemetry to the Phase 0 backend.

Sketch folder: [`LPG_Device/`](LPG_Device/) (open `LPG_Device.ino` in the Arduino IDE).

## Things I found that you should know

1. **R0 definition would have made clean air read ~577 ppm.** With your curve
   `log10(Rs/R0) = 1.27 - 0.46*log10(ppm)`, `Rs/R0 = 1` means 577 ppm. In clean air the
   datasheet ratio is about 9.8 (about 4 ppm). If R0 were set to the raw clean-air
   resistance, clean air would read ~577 ppm and the fan would run permanently.
   So `CALIBRATE_MODE` prints **`R0 = Rs_cleanair / 9.8`** ready to paste. This is the
   one deliberate deviation from "R0 = clean-air resistance".
2. **Relay polarity (unproven, best guess = active-LOW).** Your old sketch drove the pin
   LOW to switch the fan on and released it to float (module pull-up) to switch it off.
   That is active-LOW behaviour, so `RELAY_ACTIVE_LOW` defaults to `true`. Confirm with
   `HARDWARE_TEST_MODE` and record the date in `config.h`.
3. **The old servo logic was not actually inverted.** `90` on gas and `0` on normal is
   consistent with "0 = closed, 90 = open". What was wrong: it also parked the flap
   **open (90)** at boot, and it was binary. The new firmware parks closed and is
   proportional (45% / 90%). I could not move your real flap, so confirm the direction
   with `HARDWARE_TEST_MODE`; if reversed, swap `SERVO_CLOSED_DEG` / `SERVO_OPEN_DEG`.
4. **Gas pin changed.** The old sketch read a digital pin 22 (module DO). The new one
   reads **analog GPIO34 (AO)** through your voltage divider. Set the real divider
   resistors and the module's load resistor `RL` in `config.h` (placeholders marked TODO).
5. **The DHT22 only refreshes every 2 s.** The firmware reads at 1 Hz, but the Adafruit
   library returns the cached value in between, so humidity updates every other second.
   Serial shows `(DHT stale)` when a read actually fails. This is a sensor limit, not a bug.
6. **Backend features differ from the 9 you listed.** The backend computes 7
   (`ppm_comp, d_ppm_5s, slope_30s, ma10, ma30, d_rh_10s, tt700_s`) and its
   `ppm_comp` equals `ppm_raw` (no temperature/RH compensation yet). The firmware
   computes your 9 (adding `temp_c`, `rh_pct`, in your order) with `ppm_comp = ppm`, identical
   to the backend. When you add the model, check the order against `lpg_model_card.json`
   (there is no model card in the repo to read).
7. **The preview backend could not be reached by the ESP32.** `backend/preview_stack.py`
   bound its broker to `127.0.0.1` only. I added two environment switches (below). Its
   built-in LPG simulator also publishes as `lpg01`, so it must be switched off when the
   real device is running.
8. **`mqtt_client.h` shares a name with an ESP-IDF header.** The sketch's own copy is
   found first because it is included with quotes, and it compiled fine. If you ever
   see an odd include error, renaming it is the fix.

## Configure `config.h`

1. `WIFI_SSID`, `WIFI_PASSWORD`. **Do not commit real credentials to git.**
2. `MQTT_HOST`: the **LAN IP of the PC running the broker** (not `127.0.0.1`).
3. `MQTT_PORT` stays `1883`; `MQTT_USER/PASS` empty for the anonymous dev broker.
4. `MQ2_RL_OHM`: the load resistor on your MQ-2 module (SMD marking `502` = 5 kΩ,
   `102` = 1 kΩ, `103` = 10 kΩ).
5. `DIVIDER_R_TOP_OHM`, `DIVIDER_R_BOTTOM_OHM`: your real divider resistors. The GPIO34
   pin must never exceed 3.3 V.
6. Leave `MQ2_R0_OHM` for now; you set it in the calibration step.
7. Device ID is `lpg01`, matching the backend and the app (`LPG_DEVICE_ID`).

## Step 1: Hardware bench test (relay polarity, servo direction, buzzer)

Do this **before** trusting any safety logic. Disconnect anything dangerous from the
relay's load side or test with the fan only.

1. In `config.h` set `HARDWARE_TEST_MODE true`. Flash. Open Serial Monitor at **115200**.
2. Every 4 seconds it prints a prompt and does one thing: relay "on" level, relay "off"
   level, servo closed angle, servo open angle, buzzer on, buzzer off.
3. Fan runs when the prompt says "ON level" -> polarity setting is correct. If it runs
   at the "OFF" prompt, flip `RELAY_ACTIVE_LOW`.
4. At the "CLOSED" prompt the flap should be shut and at "OPEN" open. If reversed, swap
   `SERVO_CLOSED_DEG` and `SERVO_OPEN_DEG`. Check the flap does not jam at 90 deg; lower
   `SERVO_OPEN_DEG` if it does.
5. Set `HARDWARE_TEST_MODE false` again. Tell me what you found if it differs from the
   defaults (I did not flip anything silently).

## Step 2: Calibrate the MQ-2 (R0)

1. Complete the **48 h burn-in** with the sensor powered.
2. Set `CALIBRATE_MODE true`, flash, open Serial Monitor at 115200.
3. Put the sensor in **clean, ventilated air** (no cooking, lighter gas or aerosol nearby)
   for at least 10 minutes.
4. Each second it prints the raw ADC count, pin and sensor millivolts, `Rs`, `Rs/RL`, a
   60-second stability figure, and `Suggested MQ2_R0_OHM = ...`.
5. When the line says `STABLE` (std-dev under ~2% for 60 s), note the **Suggested
   MQ2_R0_OHM** value.
6. Put that number into `config.h` as `MQ2_R0_OHM`. Set `CALIBRATE_MODE false`. Flash.
7. Sanity check: in clean air the normal firmware should now show roughly 3 to 10 ppm,
   i.e. tier Safe. Serial prints a warning at boot while R0 is still the 10000 placeholder.

Note: the MQ-2's datasheet range is 200 to 10000 ppm; readings below ~200 ppm are
indicative only. Repeat calibration if the sensor is replaced.

## Step 3: Backend and broker

The ESP32 must reach the MQTT broker on your LAN. Choose one:

**Docker (recommended for the real device):** `docker compose up --build`. Mosquitto
listens on all interfaces, port 1883. Do **not** also run the LPG simulator
(`simulators/run_all.py` starts it); run the others individually if you need them.

**Preview stack:** `backend/preview_stack.py` now listens on `0.0.0.0` by default and starts
the pantry, pest and child simulators but **not** the LPG one (it would publish as `lpg01`,
the real device's id):

```powershell
python .\backend\preview_stack.py
# startup prints:  [preview] MQTT broker listening on 0.0.0.0:1883
#                  [preview] simulators ON: pest, child; OFF (real hardware owns these ids): lpg, pantry
```

Simulators now default to **pest and child only**, because the LPG and pantry simulators
publish under the same device ids as the real boards (`lpg01`, `pantry01`). Opt-ins:
`$env:PREVIEW_SIMULATORS = "lpg,pantry,pest,child"` (or `.\scripts\dev_stack.ps1 -WithSimulators`)

Windows Firewall must allow inbound TCP 1883 (private network). Find the PC's IP with
`ipconfig` and put it in `MQTT_HOST`. The phone app keeps using

## Step 4: Flash and watch

Set `CALIBRATE_MODE false`, `HARDWARE_TEST_MODE false`, upload, open Serial at 115200:

```
[SELFTEST] features=ok sensors=ok tier-logic=ok
[MODEL] RULE FALLBACK (lpg_rf_esp32.h not found - not the trained model)
[   12s] ppm=    4.2 tier=Safe      (raw Safe     ) fan=OFF win=  0% T=30.1C RH=67.0% net=ONLINE seq=11
```

Each line: ppm, active (debounced) tier, raw tier, `OVERRIDE` when >= 700 ppm, fan,
window percent, temperature, humidity, network state, sequence, `WARMUP` for the first
30 s. New `telemetry_lpg` documents appear in the backend as soon as `net=ONLINE`.

## Network troubleshooting (read the Serial log first)

The network runs on its own task, so sensing starts immediately and never waits for WiFi.
That is why no "connecting" phase appears between boot and the first `ppm=` line; the
`[WIFI]` / `[MQTT]` / `[NET]` lines are printed by that task and are interleaved with the
sensing lines. Every sensing line ends with the failing stage:

| `net=` value | Meaning |
| --- | --- |
| `OFFLINE(wifi)` | ESP32 is not connected to the WiFi network |
| `OFFLINE(mqtt)` | WiFi is up but the MQTT broker connection failed |
| `ONLINE` | WiFi + MQTT up, telemetry flowing |

Boot log lines to look for, in order:

1. `[NET] network task started. WiFi SSID "..." (N chars), password N chars, broker ...`
   confirms exactly what the firmware thinks it was configured with (catches typos and
   stray spaces; the password is shown only as a length).
2. `[WIFI] scanning ...` then a numbered list of every network the ESP32 can see, with the
   configured one marked `<== your WIFI_SSID`. **If your network is not in this list, the ESP32
   cannot join it, whatever the password is.**
3. `[WIFI] disconnected, reason N = ...` gives the real reason (201 = SSID not visible,
   202/15/204 = wrong password, 200 = signal lost).
4. `[WIFI] connected: IP ...` and a warning if the broker is on a different subnet.
5. `[MQTT] connect FAILED, state N = ...` with a plain-language cause (-2 = could not open
   a TCP connection to the broker).
6. `[NET] ONLINE.` once everything is up, `[NET] now OFFLINE: ...` with the reason if it drops.

### Causes found on the first bring-up (all three must be fixed)

1. **5 GHz WiFi.** The SSID was `Dialog 5G 862 5GHz` (802.11ac, channel 36). The ESP32
   radio is **2.4 GHz only**, so it cannot even see that network. Use the router's 2.4 GHz
   network (often a separate name such as `Dialog 4G ...`; enable it in the router page if
   it is hidden or off) or a phone hotspot set to 2.4 GHz, and put that name in `WIFI_SSID`.
   The laptop and ESP32 must be on the **same** network.
2. **Broker only listening on localhost.** `backend/preview_stack.py` binds the MQTT broker to
   `127.0.0.1` (before this fix), so only programs on the laptop could reach it. It now defaults
   to `0.0.0.0`; restart it and look for `[preview] MQTT broker listening on 0.0.0.0:1883`:
   ```powershell
   python .\backend\preview_stack.py
   ```
   Note: the backend log line "Connected to MQTT broker 127.0.0.1:1883" is the backend's own
   *client* connecting to the broker on the same laptop; it is expected and does NOT show the
   broker's bind address.
   Verify with `Get-NetTCPConnection -State Listen -LocalPort 1883`: `LocalAddress` must be
   `0.0.0.0`, not `127.0.0.1`.
3. **Windows Firewall.** No inbound rule for TCP 1883 existed. In an **Administrator**
   PowerShell:
   ```powershell
   New-NetFirewallRule -DisplayName "KitchenGuard MQTT 1883" -Direction Inbound `
     -Protocol TCP -LocalPort 1883 -Action Allow -Profile Private
   ```
   If Windows classed your WiFi as *Public*, set it to *Private* or add `Public` to `-Profile`.

Also re-check `MQTT_HOST` whenever the laptop's address changes (DHCP can change it):
run `ipconfig` and use the **IPv4 Address** of the WiFi adapter.

### Every-time checklist (laptop restart, new ESP32, or "net=OFFLINE(mqtt)")

Run `.\scripts\dev_stack.ps1 -CheckOnly` first; it checks the items below and prints the
exact fix for each one. To start the backend for real devices use `.\scripts\dev_stack.ps1`.

1. Laptop and ESP32 are on the **same 2.4 GHz** network (`[WIFI] got IP` line in Serial).
2. `ipconfig` IPv4 equals `MQTT_HOST` in `config.h` (DHCP can change it; re-flash if so).
3. Network profile is **Private**; firewall has the TCP 1883 inbound rule (one-time, admin).
4. Broker listens on `0.0.0.0:1883`, not `127.0.0.1` (`Get-NetTCPConnection -State Listen -LocalPort 1883`).
5. No simulator is publishing as the same `device_id`.
6. Serial shows `[MQTT] connected` then `net=ONLINE`; `.../lpg01/latest` matches the Serial line.

Error to cause: `OFFLINE(wifi)` = SSID/password/band; `OFFLINE(mqtt)` + `state -2` = broker
unreachable (items 2 to 4); `state 4/5` = broker wants credentials.
Pantry and pest devices use the same broker, so items 1 to 4 are one-time per laptop/network.

## Debugging commands and actuators (Serial log guide)

Every command and every actuator change leaves a trace, in this order:

| Log line | Meaning |
| --- | --- |
| backend: `cmd -> kitchenguard/lpg/lpg01/cmd action=fan value=0.0 source=manual publisher=ready` | the backend sent it (and with what value) |
| `[MQTT] rx cmd: {...}` | the device received that exact JSON. If this line is missing, the command never arrived |
| `[MQTT] cmd ignored: ...` | arrived but rejected (wrong device, unsupported action such as `buzzer`, bad JSON) |
| `[CMD] fan=0.00 ... active tier=Safe \| fan ON->OFF window 0%->0% \| APPLIED` | decision, plus fan and window **before/after**, so you can see a command touched only its own actuator |
| `[CMD] ... IGNORED - refused: tier is Critical` | the safety refusal (only at the debounced Critical tier) |
| `[ACT] fan ON -> OFF (manual hold, active tier Safe)` | the relay really changed, and **why** (`manual hold`, `auto from tier`, `CRITICAL override`) |
| `[ACT] window 0% -> 100% (...)`, `[ACT] buzzer mode: PULSING ...` | same for the window and buzzer |
| `... hold=[fan window]` at the end of the 1 Hz line | which manual holds are active |
| `[BOOT] reset reason: BROWNOUT` | the chip lost power: a supply/ground problem, not software |

The buzzer is **automatic only** (Dangerous = pulsing, Critical = continuous). The spec's manual
commands are `fan` and `window`; the app has no buzzer control, and a `buzzer` command is logged
as unsupported.

**Bench-testing tiers without gas:** set `DEBUG_FORCE_PPM` in `config.h` (350 = Dangerous,
800 = Critical), flash, test, then set it back to `-1` and flash again. While it is set the sensor
is ignored, telemetry carries the fake value and every Serial line is tagged `[DEBUG: PPM FORCED]`.

## Behaviour reference

| Active tier | Fan | Window | Buzzer |
| --- | --- | --- | --- |
| Safe | off | 0% | off |
| Warning | off | 0% | off (dashboard alert only) |
| Dangerous | ON | 45% | pulsing 500 ms on / 500 ms off |
| Critical | ON | 90% | continuous |

- **Rules/model tiers:** `<150` Safe, `<300` Warning, `<700` Dangerous, else Critical.
- **Hard override:** `ppm_comp >= 700` forces Critical. It is applied after the model, is
  never debounced, and acts within the same 1-second sample.
- **Debounce:** any other tier change needs 3 consecutive 1 Hz readings.
- **Hysteresis (added):** once Critical, the tier is held until ppm falls to **630 or
  below**, then the 3 s debounce applies on the way down. This stops the fan chattering
  around 700. Change `OVERRIDE_CLEAR_PPM` if you want it tighter.
- **Servo:** moves smoothly (90 deg/s) to avoid current spikes on the separate supply.
  `window_frac` in telemetry is the commanded fraction.
- **Boot:** relay off, buzzer off, flap closed before anything else runs.
- **Sensor fault:** if AO reads about 0 V (unpowered or disconnected), that is **not** clean
  air. The firmware prints `SENSOR FAULT`, keeps its current actuation and does not
  publish bogus data. It does not yet raise a physical alarm for a dead sensor
  (see "Not done").

## Edge failsafe (works with no network)

`loop()` on core 1 does sensing, features, classification, override, debounce and
actuation. All WiFi/MQTT work runs in a separate task on core 0 and talks to `loop()` only
through two small queues, so a failed connect (which can block for seconds) can never stall
the 1 Hz loop or an actuation. While offline, samples are stored with
`edge_offline_mode = true` (up to 120, about 2 minutes; the oldest are dropped first) and
are published automatically after reconnection. WiFi and MQTT are retried in the
background (every 10 s and 5 s).

**Timestamps:** the ESP32 system clock is set once by NTP (`pool.ntp.org`,
`time.google.com`) and keeps counting by itself afterwards, so timestamps stay correct
while offline. A sample taken before the first sync is back-dated from uptime when it is
published. If the device has never synced, it holds those samples (it will not invent
1970 timestamps).

## MQTT contract

| Topic | Direction | Payload |
| --- | --- | --- |
| `kitchenguard/lpg/lpg01/telemetry` | device -> backend, 1/s | `LpgTelemetry`, exactly these keys: `schema_version, device_id, ts, seq, ppm_raw, temp_c, rh_pct, fan_on, window_frac, edge_tier, edge_offline_mode` |
| `kitchenguard/lpg/lpg01/status` | device -> backend, **retained** | `{"status":"online"}` on connect; Last Will `{"status":"offline"}` |
| `kitchenguard/lpg/lpg01/cmd` | backend -> device | `ActuatorCommand`; the device reads `device_id`, `component`, `action` (`fan`/`window`), `value`, `source` |

`ppm_raw` carries the converted ppm value (the same meaning as in your simulator).
No field was renamed or added.

**Manual commands:** `fan` value >= 0.5 is on. `window` value is the open fraction 0 to 1.
Commands are obeyed, **except at Critical**: turning the fan off, or closing the window
below 90%, is refused and logged (`[CMD] ... IGNORED - refused: tier is Critical`). A manual
setting is held until the active tier changes or 15 minutes pass (`MANUAL_HOLD_S`), then
automatic control resumes. Note: per your spec only Critical blocks manual "off"; at
Dangerous a manual off is allowed. Say so if you want Dangerous protected as well.

The backend also publishes an automatic `fan=1` (`source: override`) when it sees
Critical; the device accepts it as a normal command.

## Dropping in the trained model

1. Copy `lpg_rf_esp32.h` (micromlgen output, class `Eloquent::ML::Port::RandomForest`,
   `predict(float*)` returning 0 to 3) **into `LPG_Device/`**.
2. Open `lpg_model_card.json` and check the feature order equals
   `ppm_comp, d_ppm_5s, slope_30s, ma10, ma30, temp_c, rh_pct, d_rh_10s, tt700_s`.
   If not, reorder `FeatureVector::toArray()` in `features.h`.
3. Re-flash. Boot Serial prints `[MODEL] trained Random Forest` and the fallback warning
   disappears. The 700 ppm override still applies on top of the model.

## Acceptance checklist

- [ ] `CALIBRATE_MODE` prints stable Rs and a suggested R0 (needs your sensor)
- [ ] Normal mode: clean Serial line each second; `telemetry_lpg` documents appear
- [ ] Unplug WiFi: Serial shows `net=OFFLINE`, fan/servo/buzzer still react; on reconnect
      the backlog arrives with `edge_offline_mode: true`
- [ ] Gas near the sensor (ventilated area): tier changes within a few seconds
- [ ] ppm >= 700 (real or forced): relay, servo and buzzer act within 1 s
- [ ] `POST /api/lpg/lpg01/cmd` fan-on obeyed within a couple of seconds (`[CMD]` line)

To test the override without gas, temporarily lower `TIER_CRITICAL_PPM` in `config.h`
(e.g. to 50), blow on the sensor, then restore **700**.

## Not done / limitations

- No temperature/humidity compensation of ppm (the backend has the same TODO).
- A dead or disconnected MQ-2 is detected and logged, but it does not sound an alarm.
- Only one WiFi network and no provisioning UI; credentials live in `config.h`.
- MQTT is unauthenticated and unencrypted (dev broker). Add TLS/auth before deployment.
- Publishing is QoS 0; the command subscription is QoS 1.
